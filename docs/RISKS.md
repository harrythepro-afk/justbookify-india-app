# Risks

Reviewed at the end of every phase.

| # | Risk | Why it matters | Mitigation | Severity | Status |
| --- | --- | --- | --- | --- | --- |
| 1 | Checkout apps behave differently inside the app | ACOD and SMART Checkout Rules alter checkout and must work inside Checkout Kit | Early check 2. Passed on Android on 3 October 2026 (P3-02): rates, discount, R2, R3 and ACOD all behave as on the live store's settings. Repeat on iPhone in P9-02, moved after Phase 10's start and due before Phase 12 (D-158) | High | Open for iOS only |
| 2 | Razorpay redirect and UPI hand-off inside an in-app checkout | A payment could fail or strand the customer between apps | Early checks 1a and 1b, at an owner-approved launch rehearsal on the live store in Phase 19, with one small real order (D-033). They cannot run earlier: Razorpay needs an Indian business entity and the development store's is in Bahrain. Fallback: checkout in the system browser with a return link, chosen by a remote feature flag built with the checkout screens in Phase 9, so a failure at the rehearsal needs no rebuild. Since P9-01 the flag is read afresh each time checkout opens and fetched on each return to the foreground, so a change applies at the next checkout after a fetch saw it, with no restart (D-150); the browser presentation is built (D-152) | High | Open until the rehearsal |
| 3 | Rental records may be incomplete | About 600 fulfilled orders have no return recorded | Spot-check the oldest before launch | High | Open |
| 4 | Old books not collected when a new order arrives | A family may hold two sets | Show the books due for collection at checkout | High | Open |
| 5 | Testing on the live store | Test orders remove real books and trigger deliveries | Development stores only; one approved launch rehearsal, which also runs early checks 1a and 1b (D-033). P9-01's cash-on-delivery test orders are on the development store only, each with the owner's yes, after `npm run check:dev-store` confirms the store (D-146, D-155) | High | Open |
| 6 | Cash-on-delivery abuse | Orders take books out of circulation without payment | Login required; rate limits; integrity checks | Medium | Open |
| 7 | Return requests do not reach staff | A new return path through the Admin API | Early check 4, run in Phase 10, backend foundation (D-034); fallback is the same email the website sends | Medium | Open |
| 8 | App Store rejection for minimum functionality | A thin wrapper is refused | Native browsing, rental status and notifications | Medium | Open |
| 9 | Half the catalogue is unavailable | Disappointing browsing | "Available now" as the default filter; notify-me | Medium | Open |
| 10 | Privileged token leak | Exposes customers' addresses and phone numbers | Server-only tokens; least scopes; rotation | Medium | Open |
| 11 | Developer accounts are in an individual's name | The business is a sole proprietorship today | Move the app to the company's accounts once the company exists. This includes the EAS project, which is on the owner's personal Expo account (D-028) | Medium | Open |
| 12 | Deep-link verification on a Shopify-hosted domain | Links may not open the app | Early check 5, run in Phase 12, notifications and deep links (D-034); fallback is a link subdomain | Medium | Open |
| 13 | WhatsApp consent gap | Reminders go to the checkout phone number with no separate consent | Owner to review with a local adviser; the app collects its own consent | Medium | Open |
| 14 | Reviews API not available on the store's plan | Reviews are in version 1 | Early check 6, run in Phase 13 with reviews (D-034); fallback is ratings only | Medium | Open |
| 15 | Dependency churn | Checkout Kit is being renamed; Expo and store rules change yearly. On 3 October 2026 the planned `@shopify/checkout-sheet-kit` 4.0.x was not yet published, and the renamed package was alpha only | Pin versions; quarterly upgrade window; 3.9.1 pinned until 4.x is stable (D-030); re-checked 15 October 2026, still no 4.x (D-147) | Low | Open |
| 16 | Damaged ISBN and barcode data | Cannot be used for lookups | Do not rely on barcodes in version 1 | Low | Open |
| 17 | Vulnerable URL parser in the deep-link path | Expo Router's `query-string` depends on `decode-uri-component` (GHSA-vcc3-ghjq-m6fr, affects 0.4.2 and below). A malformed percent-encoded link could stall the app's JavaScript thread. The fix is a major upgrade of `query-string` under Expo Router, deferred on 2026-10-03 | Must be fixed or mitigated before deep links are enabled in Phase 12. Re-check at every Expo upgrade, since a later Expo Router may carry the fix | Medium | Open |
| 18 | `main` without branch protection | GitHub refused protection for the private repository on 3 October 2026 (HTTP 403): it needs GitHub Pro or a public repository. Without it, direct pushes, force pushes and merges without passing CI are technically possible | **Since 15 October 2026, while the repository is public (D-144), `main` is protected (D-145):** a pull request and the checks "Lint, types, tests, audit" and "Secret scan" before any merge, admins included; no force push or deletion. The merge rule in `CLAUDE.md` still applies on top (pull requests only, CI green on the latest commit, merge only on the owner's "approved, merge"). If the repository goes private again without GitHub Pro, the protection is lost and the merge rule is again the only gate | Medium | Mitigated while public |
| 19 | Crash reporting unproven on a release build | P4-02 proved handled JavaScript errors reach Sentry without personal data, on a development build only. A development build cannot show a native crash (the dev client catches it) and does not upload source maps. A tester's crash could go unrecorded, be unreadable, or carry an IP address, city, device ID, store domain or token | Release gate in `TESTING.md`: no build goes to any tester other than the owner until, on a staging build, a real native crash arrives in Sentry, source maps upload and the stack trace is readable, and the raw crash event shows none of those fields | Medium | Open until the gate passes |
| 20 | Feature flags silently stop reaching phones | A build pointed at the wrong Firebase project, or a Phase 14 API key restriction that blocks Remote Config, leaves every phone on its last values or the defaults. Ordinary fetch failures are deliberately not reported to Sentry (D-046), so nothing would alert | Release gate in `TESTING.md` ("Release gate: feature flags"): every staging and production build is shown to fetch a changed flag before release, and again after the key restriction. Each environment has its own `google-services.json`, and a build without one fails (D-044) | Medium | Open |
| 21 | The store's privacy policy does not cover the app | The app collects analytics under consent, links usage to the customer account after login (D-050), keeps it 14 months (D-051), reports the install source (D-049), sends crash reports to Sentry and uses Firebase (Remote Config, Installations, Analytics). Since P6-09 it also records, under consent, the catalogue events (`view_collection`, `view_book`, `filter_applied`, `search`) and, for a search, which catalogue item the term matched, by ID or code, never the term itself (D-108, D-109). An outside tester would be using an app whose data practices the published policy does not describe | **The owner's task:** before any outside tester, add an app section to the store's privacy policy covering analytics consent, usage linked to the customer account, the 14-month retention, install-source reporting, the events and data Firebase sends by itself (`ANALYTICS.md`), the app's own events including the catalogue events, that under consent the app records which catalogue item a search matched (P6-09), crash reports and Firebase, reviewed by a local adviser together with the draft consent wording: the consent request (P7-03, D-130) and the Account switch, whose description now says usage is linked to the account when logged in. Part of the release gate in `TESTING.md` ("Release gate: analytics consent"). Publishing it on the live store is the owner's action | Medium | Open |
| 22 | A false "offline" hides fresh books and stops reading | Seen once on 7 October 2026 (P6-03 phone check): after more than 5 minutes in the background the app's query cache said offline while the phone was online, so queries stayed paused, the screen kept old books under "You're offline. Showing saved books.", and a tab switch did not help. Not reproduced in two later runs; the cause is unproven. Android was seen reporting "not connected" to the app while it was in the background with Wi-Fi on | D-082: the app re-reads the network on every return to the foreground, re-reads every 3 seconds while it is in the foreground and counts as offline, and every "Try again" re-reads before it refetches. The development tools keep the last 10 network events. A standing step in every phone check: after more than 5 minutes in the background, no false offline notice (`TESTING.md`). **D-111 (P6-10) closes the question** of whether queries should stop pausing on the platform's signal: they keep pausing, with D-082's safety net, on the evidence of no false offline in the standing step of the phone checks from P6-04 to P6-09. The standing step stays in every phone check until the first release build, and is reviewed then | Medium | Mitigated |
| 23 | A login lost when Android ends the app during login | If Android ends the app's process while Shopify's login page is open in the Custom Tab (low memory, or the phone's own battery rules), `expo-auth-session` returns `dismiss` and that login cannot be finished: the PKCE verifier lived in the ended process (expo/expo#44284). The customer sees "Log in" again and has to repeat the emailed code | D-119: the customer taps "Log in" again; the callback URL then opens the Account tab and never reaches a route (D-120). Expo's proxy activity (the default) keeps the login page alive when the app goes to the background. `react-native-app-auth` 8.5.0 could resume such a login; the owner chose `expo-auth-session` (P7-01). Watch for it in phone checks and beta feedback | Low | Open |
| 24 | A website logout does not end the app's login | By the owner's rule (answer 3, D-122) the app stays logged in after the customer logs out on the website, until Shopify refuses the refresh token or the customer taps "Log out". A customer who logs out on the website of a shared phone may expect the app to follow. Shopify's docs say nothing on whether a website logout ends a mobile client's refresh token (read 13 October 2026) | The owner's decision; the phone check (P7-01 step 3) records what Shopify does on the development store. "Log out" in the app logs out on the phone and calls Shopify's mobile logout | Low | Accepted |
| 25 | The repository is public | Since 15 October 2026 (D-144, after GitHub billing stopped CI) anyone can read the code, the docs and the whole history, and anyone can open pull requests, issues and comments. A secret committed by mistake would be exposed at once; a pull request or comment from someone else could carry harmful code or instructions | Nothing secret ever goes into the repository (`SECURITY.md`); the secret scan runs on every push and pull request; gitleaks found no leaks in all 201 commits before the change. Never merge, check out or run code from a pull request, issue or comment by anyone other than this project's own work (`CLAUDE.md`). `main` is protected (D-145). Back to private when GitHub Pro arrives | Medium | Open while public |
| 26 | Shopify may refuse a customer's token sent from the backend | The backend derives the customer from the Customer Account API with the customer's own token (D-161). Shopify documents that token for the app's own calls; it neither describes nor forbids a server making the same call, and P10-01 can test it only with Shopify faked. If Shopify refuses it (for example by origin, user agent or IP), every backend job that needs the customer's identity (returns, back-in-stock alerts, push registration, the analytics user ID) needs another design | P10-02's first check, with a real login on the phone against the deployed development backend. If Shopify refuses it, the work stops for the owner; the alternatives (a confidential client, an Admin API lookup) need decisions and secrets | Medium | Open until P10-02 |
| 27 | The backend reachable by scripts once deployed | A public HTTPS endpoint can be called by anyone with a valid-looking token, or flooded; each call costs money and uses Shopify's per-customer request limit (threat 1 in `SECURITY.md`) | **Required before any non-development backend deploy** (owner, P10-01): per-customer and per-device rate limits, and Firebase App Check (Play Integrity, App Attest) on backend endpoints. Until then: `maxInstances` 5 as a cost cap, the identity check on every request, `whoami` only in development (D-162) | Medium | Open |
